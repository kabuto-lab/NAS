1 · Что это

Это не чат-бот, который пишет код. Это персистентная многоагентная инженерная когниция — система из 14-ти специализированных «умов» с конфликтующими приоритетами, которая принимает архитектурные решения о продукте AX•CMS на горизонте 12 месяцев.

Каждый «ум» — это не персонаж и не roleplay. Это когнитивная специализация, которую AI применяет к одному и тому же артефакту с разных углов. Все 14 умов:

  • читают одну и ту же 12-месячную карту (WP-PLAN-12-MONTH.html);
  • читают одну и ту же конституцию платформы (ENTITY.md);
  • читают одну и ту же конституцию своего поведения (CONSTITUTION.md);
  • пишут в общую память (memory/) — каждый в своё досье;
  • обязаны спорить. Консенсус с первого раза считается подозрительным.
Главная идея. 12-месячные роадмапы умирают не от багов в коде, а от дрейфа: забытых допущений, локальных оптимизаций, фрагментации архитектуры, невидимого технического долга. Совет существует, чтобы дрейф обнаруживать каждый день и чинить в течение фиксированного окна.

2 · Зачем — проблема, которую решает Совет

В одиночку (один «ассистент» = один прогон) AI на длинных проектах деградирует так:

СимптомЧто происходитКогда это «прилетит»
DriftРешение M3 противоречит решению M7, ни один документ не зафиксировал переходM5–M7
EntropyАрхитектура расползается на 5 слабосвязанных подсистемM6+
Local optimizationПерформанс одного хэндлера задушил cache layerлюбой бенчмарк-день
Forgotten assumptions«мы решили в M2, что …» — но в M9 этого никто не помнитM8–M12
Invisible debtWIP-ADR, который никогда не был ратифицирован, превратился в фактический контрактM9+
Architecture fragmentationEditor → один стек, Theme → другой, Plugin → третий, миграция невозможнаM10+

Совет противодействует этому встроенным напряжением (Tension Doctrine, CONSTITUTION.md §2): консенсус с первого захода обязателен к оспариванию. Согласие = ленивая выдача, пока Simplifier не попытался что-нибудь удалить.

3 · Топология — «осьминог»

┌──────────────────────┐ │ ОПЕРАТОР │ ← человек; суверен │ (единый суверен) │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ КОНСТИТУЦИЯ │ ← доктрина (4 файла) │ (неподвижный код) │ не сущность └──────────┬───────────┘ │ связывает ▼ ┌─────────────────── ГОЛОВА: ORCHESTRATOR ────────────────┐ │ │ │ Tier-1 · Ядро (всегда на связи) │ │ ▸ ORCHESTRATOR — главный архитектор │ │ ▸ FORGEMASTER — runtime / perf / Rust │ │ ▸ SENTINEL — отказы / безопасность │ │ │ │ Tier-2 · Стабильность (ежедневно) │ │ ▸ SIMPLIFIER — анти-overengineering │ │ ▸ HISTORIAN — память решений │ │ ▸ ECONOMIST — стоимость / сложность │ │ │ │ Tier-3 · Атака (по триггеру / еженедельно) │ │ ▸ ADVERSARY — угрозы / эксплоиты │ │ ▸ CHAOS — partition / cascading failure │ │ ▸ TEST PILOT — нагрузка / насыщение │ │ │ │ Tier-4 · Эволюция (помесячно / по триггеру) │ │ ▸ MIGRATOR — риск переписывания │ │ ▸ ECOSYSTEM — SDK / сторонние │ │ ▸ PRODUCTOR — UX / DX / эргономика │ │ │ │ Tier-5 · Мета (только на тупике) │ │ ▸ JUDGE — детерминированный арбитр │ └─────────────────────────────────────────────────────────┘

Оператор стоит вне Совета. Его прямое указание в живой сессии перебивает любую сущность и любое правило — кроме трёх жёстких ограничений (CONSTITUTION.md §12): git push только по явной команде, изменения spine-файлов только по явной команде, и нарушения ENTITY.md §3 (стек) не сохраняются в постоянную память.

4 · 14 сущностей — кто чем занят

Каждая карточка — ум Совета. Цвет слева = уровень (Tier). Полное досье в docs/governance/ENTITY_SYSTEM.md.

ORCHESTRATOR
Tier-1 · ГОЛОВА · главный архитектор

Держит весь 12-месячный план, граф зависимостей, философию платформы. Мыслит годами и экосистемами, не деталями.

Спрашивает: «Это станет узким горлом к M9? Это переживёт мультитенантность?»
FORGEMASTER
Tier-1 · runtime / perf / Rust

Сеньор Rust-инженер. Считает аллокации, lock surface, cache lines, async overhead, throughput.

Спрашивает: «Где лишние аллокации? Этот Arc> действительно нужен? Какой бенч это докажет?»
SENTINEL
Tier-1 · отказы / безопасность

«Производственная паранойя». Моделирует обвалы, эксплоиты, rollback, observability gaps.

Спрашивает: «Как это сломается? Что если Dragonfly недоступен 30 минут? Заметит ли monitoring до пэйджа?»
SIMPLIFIER
Tier-2 · анти-overengineering

Самая недооценённая сущность. Удаляет лишние абстракции прежде, чем они приживутся.

Спрашивает: «Почему нельзя проще? Что произойдёт, если удалить этот слой?»
HISTORIAN
Tier-2 · память решений

Ведёт decision-graph.md. Anti-amnesia модуль: следит, чтобы новые ADR не противоречили старым тихо.

Спрашивает: «Это уже отвергалось? Кто supersedes кого?»
ECONOMIST
Tier-2 · стоимость / сложность

Считает $/месяц, engineer-weeks, MTTR, кривые масштабирования. Отказывает в «бесконечно-масштабируемых» претензиях без матмодели.

Спрашивает: «Сколько это стоит при 10K тенантов? Окупается ли?»
ADVERSARY
Tier-3 · угрозы / эксплоиты

Моделирует умного атакующего с доступом к исходникам. STRIDE, OWASP, supply chain, multi-tenant leakage.

Спрашивает: «Может ли тенант A прочитать данные тенанта B? Где race condition в RLS?»
CHAOS
Tier-3 · partition / cascading

Моделирует разрывы сети, дисковые тормоза, потерянные сообщения, cache stampede, thundering herd.

Спрашивает: «Что если NATS теряет 10% сообщений инвалидации? Что после network heal?»
TEST PILOT
Tier-3 · нагрузка / насыщение

Где p99 при 80% насыщении? Head-of-line blocking? Кривые насыщения. Среднее всегда обманывает — смотрит хвост.

Спрашивает: «На какой RPS этот хэндлер начинает деградировать?»
MIGRATOR
Tier-4 · риск переписывания

На горизонте 18 мес. — какие подсистемы потребуют rewrite? Semver impact. Vendor lock-in. WP-import fidelity.

Спрашивает: «Если мы поменяем этот API через полгода — что будет с плагинами?»
ECOSYSTEM
Tier-4 · SDK / сторонние

Эргономика SDK для плагинов и тем. CMS умирают без экосистемной гравитации — здесь это первичная забота.

Спрашивает: «Сколько LOC «hello-world plugin»? Авторы плагинов это поймут?»
PRODUCTOR
Tier-4 · UX / DX / эргономика

Время до первой публикации. Понятность CLI-ошибок. Чтобы система не стала технически блестящей, но непользуемой.

Спрашивает: «Сможет ли новый автор опубликовать пост за 5 минут?»
JUDGE
Tier-5 · арбитр

Вызывается только при тупике. Не голосует — выполняет детерминированный 8-шаговый алгоритм фильтров (CONSTITUTION §7).

Спрашивает: «Какая позиция стоит на более высокой ступени Priority Ladder?»
CONSTITUTION
Tier-5 · доктрина (не сущность)

Неподвижные законы. Иерархия полномочий, Priority Ladder, 14 Immutables, 14 Forbiddens, 10 Anti-Drift Laws.

Изменяется только: через формальную Motion + явное согласие оператора (§11).

5 · Ежедневный цикл Совета

Каждая AVTONOM-сессия (или MANUAL-сессия, разница в режиме) проходит через 14 фаз. Подробное определение в docs/governance/EXECUTION_PROTOCOL.md §0.

  1. T0 — Ритуал старта
    Загрузить ENTITY.md §1, CONSTITUTION.md §0+§3+§4, ENTITY_SYSTEM.md §14 (матрица активаций), MEMORY.md, досье Tier-1, вчерашний SESSION_LOG. Выдать первой строкой статус в формате CLAUDE.md §S.
  2. T1 — Read-before-trust
    Все утверждения в сегодняшнем architect.md о состоянии репозитория («файл X существует», «тест Y зелёный») проверяются Grep / Glob / cargo. Несоответствия чинятся до T2.
  3. T2 — Orchestrator
    Проверяет соответствие master-plan, граф зависимостей, forward-inheritance к будущим месяцам, дрейф-детекторы. Verdict: approve / approve-with-conditions / reject.
  4. T3 — Historian Trace
    Обновление decision-graph.md: новые узлы, новые рёбра (Supersedes / Consulted). Проверка prior-rejection. Audit ADR-aging (никакой Status: Proposed старше 7 дней).
  5. T4 — Forgemaster Memo
    Бюджет аллокаций. Lock surface. Async boundary cost. Bench / VAL slot. Static-dispatch vs dyn. Verdict.
  6. T5 — Sentinel Risk Audit
    ≥ 1 именованный failure mode с детектором и recovery path. «No concerns» — запрещён (Constitution §2.3). Threat surfaces. Rollback path. Observability hook. Invariants.
  7. T6 — Simplifier Counterproposal
    Попытка удалить ≥ 1 surface (trait, struct, layer, dep, feature flag). Forgemaster может отклонить, но Simplifier обязан попытаться.
  8. T7 — Economist Ledger
    Δ infrastructure. Per-tenant scaling curve. Maintenance cost. Учтён ли более дешёвый вариант.
  9. T8 — Tier-3 (по матрице активаций)
    Auth/RLS/upload/plugins → Adversary. Очереди/cache/edge → Chaos. Hot path → Test Pilot. На «docs-only» дни — все три skip с reason.
  10. T9 — Tier-4 (помесячно или триггер)
    Migrator + Ecosystem + Productor — на каждом RETRO, на каждом ADR с public API surface, на каждом admin-UI дне. Записывается в monthly README, не в daily.
  11. T10 — Conflict detect
    Любой reject от любой Tier-1/2/3/4 сущности или противоречие verdict — Judge вызван. 8-шаговый алгоритм (рестейт → ладдер → immutables → forbiddens → drift → выживший). Иначе — ратификация.
  12. T11 — Execute
    AVTONOM выполняет ратифицированный senior-dev.md. V1..V4 baseline → P0..PN фазы → коммиты на main (без push).
  13. T12 — Ритуал закрытия
    V1..V4 и 4 xtask-гейта зелёные. SESSION_LOG.md в корне. INDEX.md row → executed. Сущности записывают memory deltas.
  14. T13 — Anti-Drift Sweep
    D-1, D-3, D-5, D-6, D-7, D-10 проверяются ежедневно. D-2, D-4, D-9 — каждую пятницу. D-8 — каждый RETRO. Записывается в memory/orchestrator_drift_log.md.

Запуск рабочего дня

  1. Открыть терминал в корне проекта
    Windows: cd F:\Users\a\Documents\_DEV\Tran\ES\barbie\AX\NaSV2. Запустить Claude Code в этой директории. CLAUDE.md загрузится автоматически по правилам Claude Code.
  2. Открыть план дня
    Найти сегодняшнюю дату в docs/session-plans/dailies-v2/INDEX.md. Если статус ratified или adopted-pilot — план готов. Если drafted — сегодняшняя сессия начнётся с Council-pass. Если planned — план ещё не написан (требуется генерация — см. §10 FAQ).
  3. Решить режим работы
    MANUAL — обычное сообщение, без префикса. AI спрашивает по каждому развилке. Безопаснее всего, самый дорогой по вниманию.
    SEMIAUTO: — префикс SEMIAUTO: перед сообщением. AI пишет план, один MANIFEST на одобрение, потом исполняет без остановок (кроме spine-файлов).
    AVTONOM: — префикс AVTONOM:. AI работает полностью автономно по сегодняшнему senior-dev.md. spine-файлы пропускаются с записью в SESSION_LOG. git push никогда без явной команды.
  4. Открыть сегодняшний senior-dev.md
    Путь: docs/session-plans/dailies-v2/MNN-YYYY-MM/WN-YYYY-MM-DD/YYYY-MM-DD-dow/senior-dev.md. Файл начинается с AVTONOM: … — это и есть первое сообщение для AI. Скопировать его в чат целиком. (В режиме MANUAL начать с собственного задания; AI всё равно прочитает дневной артефакт.)
  5. Контролировать первую строку ответа
    AI обязан вывести: [mode:MANUAL|SEMIAUTO|AVTONOM] phase:<name> epic:<id> spine:<clear|pending>. Если этой строки нет — отказать в продолжении и попросить повторить ритуал старта (T0 EXECUTION_PROTOCOL).
  6. Дать сессии работать
    Совет проходит T0–T13 автоматически. На каждом spine-touch (см. ENTITY.md §12) сессия в MANUAL/SEMIAUTO остановится и спросит подтверждение. В AVTONOM spine-файлы пропускаются, в SESSION_LOG пишется SKIP: spine-touch on <file>.
  7. По завершении — проверить
    Открыть SESSION_LOG.md в корне. Раздел «Outcome — one line per phase» покажет, какие T-шаги были успешны. Раздел «Recommendations for human review» — что обязательно перечитать. Раздел «Commits made (local, not pushed)» — что ушло в локальные коммиты.
  8. Решить про push
    git log main --oneline -5 покажет новые коммиты. git diff main..HEAD — содержимое. Если всё ок: git push (вручную, оператор сам). Если нет: git reset --hard HEAD~N или ручные правки. Совет никогда не пушит сам.

Если что-то пошло не так

«AI не выдал first-line статус». Прервать. Дать команду: «Reset. Re-read CLAUDE.md §M and docs/governance/EXECUTION_PROTOCOL.md §1. Emit first-line status, then resume.»
«AI хочет тронуть spine-файл без причины». Отказать. Прочитать ENTITY.md §12 — там полный список. Если spine-edit реально нужен — авторизовать одной строкой в чате с указанием файла и причины; будет зафиксировано в commit message.
«AI предложил git push / force / reset --hard / pre-commit skip». Запрещено абсолютно (ENTITY.md §22.4). Отказать. Если это был AVTONOM — он не должен был это предлагать; зафиксировать инцидент в SESSION_LOG, обсудить с оператором как поломку контракта.
«AI закоммитил неконсистентные изменения». git log -1 --stat покажет, что попало. Если коммит ещё не пушнут — git reset --soft HEAD~1, разобраться, пере-коммитить корректно. Не использовать git commit --amend на коммитах прошлой сессии.

8 · Три режима — MANUAL · SEMIAUTO · AVTONOM

Аспект MANUAL SEMIAUTO: AVTONOM:
Активация обычное сообщение префикс SEMIAUTO: префикс AVTONOM:
Когда оператор отвечает на каждую развилку один раз на manifest, потом spine-touch только после сессии
AI-Defaults спрашивает применяет, записывает в commit применяет, записывает в SESSION_LOG
Spine-файлы стоп + явное OK стоп + явное OK SKIP с записью в SESSION_LOG
Council passes все 14 шагов с диалогом все 14 шагов, manifest на финал все 14 шагов без диалога
git push только по команде только по команде никогда
Когда использовать рискованные дни, ENTITY/CLAUDE.md правки, миграции хорошо очерченный план, прозрачный scope понятная задача, оператор недоступен
Совет работает на всех трёх режимах. Режим контролирует когда AI обращается к оператору, а не как тщательно сущности думают. Tier-1 ядро (Orchestrator + Forgemaster + Sentinel) всегда полное.

10 · Частые вопросы

В чём разница между ENTITY.md и CONSTITUTION.md?

ENTITY.md связывает код — что строим, какой стек, какие perf targets, что запрещено в архитектуре. CONSTITUTION.md связывает умы — как они принимают решения, разрешают конфликты, обнаруживают дрейф. Иерархия (§0 CONSTITUTION): Operator > ENTITY.md > CONSTITUTION.md > ENTITY_SYSTEM.md > …

Почему 14 сущностей, а не 1 или 100?

1 — слишком мало (нет напряжения, AI скатывается в self-confirmation). 100 — слишком много (каждая делает 1% и теряет фокус). 14 — каждая сущность держит уникальную колонку забот, без перекрытия, но с обязательными handshake'ами (см. ENTITY_SYSTEM.md §15).

Кто пишет план на завтра?

Заранее (на старте месяца) — bootstrap session, на основании MONTH-SKELETON-NN.md. Конкретный architect.md + senior-dev.md на день генерируются ИЛИ заранее (как пилотный M3 W1 D1), ИЛИ утром того дня (через RETRO предыдущего месяца). Совет на сессии запуска ратифицирует то, что увидел; если плана нет — первой фазой генерирует.

Что такое Adoption Pass и нужен ли он мне ещё?

Это одноразовый ритуал, который прошёл 2026-05-26: первая сессия после ратификации governance файлов добавила Council-секции в пилотный день и инициализировала memory/. Больше не запускается. Будущие сессии — обычный T0–T13 цикл.

Может ли Совет ошибиться?

Да. EXECUTION_PROTOCOL.md §10 перечисляет 6 режимов отказа самого Совета: quorum failure, deadlock loop, consensus theater, memory amnesia, anti-drift cascade, entity capture. На каждый описан recovery. Если Совет «залип» — оператор имеет суверенитет (CONSTITUTION §12) и перебивает напрямую.

Как менять конституцию?

Через формальный Motion: docs/governance/motions/MOT-NNN-<slug>.md → явное OK оператора → harmonization с ENTITY.md (если cross-cutting) → единый коммит с трейлером Constitutional-Amendment: MOT-NNN → roll-forward в impacted daily prompts. Амендменты никогда не применяются ретроактивно к ratified дням.

Что такое MPD (Master-Plan Diff)?

Единственный легальный способ изменить WP-PLAN-12-MONTH.html вне планового RETRO. Документ в docs/governance/master-plan-diffs/ c исходной ячейкой, предлагаемой ячейкой, обоснованием, мнением Council Tier-4, явным OK оператора. Если в M5 что-то «оказалось не так» — это открывает MPD, а не молча правится план.

Где Year-2 (M13+)?

Не существует на данном горизонте. Year-2 кандидаты сеются RETRO месяца M12 (апрель 2027) в MASTER-ROADMAP §year-2-candidates. До этого момента предложения о M13+ — это нарушение Immutable I-13.

Можно ли пропустить Совет на простом дне?

Нет. На «простом» дне (например, docs-only) Tier-1 всё равно проходит полностью; Tier-3 пропускается с явной записью Council: ADVERSARY skipped — reason: …. Implicit skip = поломка контракта (CONSTITUTION §F-1 + §2.6).
