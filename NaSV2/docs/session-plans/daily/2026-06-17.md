  ### Doc 1: `docs/rfc/RFC-001-cms-pages-publish.md`

  Skeleton:

  ```markdown
  # RFC-001 — CMS pages publish

  ## Status
  Accepted · backfilled 2026-06-17.

  ## Context
  WordPress and contemporaries store post bodies as HTML blobs. AX•CMS
  stores structured `Block` enum (heading/paragraph/image/code) for:
    - editor-time invariants (typed level enums, validated slugs)
    - server-side rendering without HTML parsing on the read path
    - migration safety (additive Block variants vs. ad-hoc HTML drift)

  ## Why
  ENTITY §11 (typed content blocks), §7 (perf targets — avoid HTML
  parse on cached read), §3.6 (sanitize on write, never on read).

  ## Decision
  See ADR-001-cms-pages-architecture.md.

  ## TLA layers
  L1 Correctness: tagged-serde Block enum forces forward-compatible
    additions; unknown variant errors are explicit JSON parse errors.
  L2 Performance: rendering = match arm dispatch, zero parsing.
  L3 Scalability: per-request render cost bounded by block count;
    cache key = tenant + slug + capability_hash (§3.9.1).
  L4 Operability: `block_type()` static-string label feeds metrics.

  ## Consequences
  + Editor UX stays typed end-to-end.
  + Render path stays allocation-light.
  − Adding new variant is a rolling deploy concern (old binaries
    return error on new tag). Mitigated via expand-only RFC discipline.

  ## References
  - ADR-001-cms-pages-architecture.md (decision)
  - VAL-001-cms-pages-tests.md (verification)
  - ENTITY §11 / §7
  ```
